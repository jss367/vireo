# Vireo - Claude Code Guide

## What is Vireo

AI-powered wildlife photo organizer. Flask backend, Jinja2 templates, vanilla JS frontend. No frontend framework.

## UI transparency is a hard rule

Read `CORE_PHILOSOPHY.md` ("Show the user what's happening / No black boxes") before writing or reviewing any user-facing status text — pills, badges, counters, summaries, "X of Y", "Already done", "Will run", readiness panels, progress phrases. Each one must answer the question users actually read it as, not a cheaper backend proxy. A pill that says "Already done" must mean *the next run would be a no-op given current settings* — not "there exists prior output somewhere." If the accurate signal needs the current UI selections (selected models, labels, variants, reclassify, etc.), build the endpoint that takes them; don't fall back to a global `COUNT(*) > 0`.

## Running

```bash
python vireo/app.py --db ~/.vireo/vireo.db --port 8080
```

## Key paths

- **App logs**: `~/.vireo/vireo.log` (RotatingFileHandler, 5MB, 3 backups). Check here first when debugging.
- **Database**: `~/.vireo/vireo.db` (SQLite, WAL mode, foreign keys ON)
- **Config**: `~/.vireo/config.json` (global settings — threshold, model, keys)
- **Thumbnails**: `~/.vireo/thumbnails/`
- **Label files**: `~/.vireo/labels/`

## Tests

```bash
# All tests (from repo root) — rarely needed locally, see below
python -m pytest tests/ vireo/tests/ -n 4 -q

# Workspace tests only
python -m pytest tests/test_workspaces.py -v

# DB tests only
python -m pytest vireo/tests/test_db.py -v
```

**Local runs share one machine — cap the workers.** Several agents often run tests at the same time on a 64 GB Mac, and each xdist worker grows to ~3 GB over a full-suite run. Never pass `-n auto` locally (it starts 16 workers): use `-n 4` at most. Run the impact-selected subset below, not the full suite; `main` runs the full suite after merge, and the `ci-full-suite` label runs it on a PR. Five concurrent `-n auto` full-suite runs once pushed the machine into ~49 GB of swap, and every run stalled.

Use `testing.waits.synchronization_timeout(seconds)` for bounded event waits,
thread joins and job polling in tests. Windows CI gets at least 30 seconds
(or three times the requested budget); local and other-platform budgets stay
unchanged. Subsecond probes, cancellation latency assertions and deliberate
timeout assertions retain their original deadlines. The shared
`vireo/tests/wait.py` polling helpers
apply this policy automatically.

Tests use temp databases. `vireo/tests/test_app.py` isolates config via `cfg.CONFIG_PATH = str(tmp_path / "config.json")` to avoid polluting `~/.vireo/config.json`.

### Impact-selected runs

The full unit suite is ~7.5k tests. `scripts/select_tests.py` maps `git diff` onto a per-test coverage map recorded on `main` and runs only the tests that executed the changed functions (whole file for changed test files; templates/static/data resolved through the Python lines that reference them). Module-level, structurally ambiguous, and harness changes fall back to the full suite because import-time dependencies cannot be represented safely by line coverage.

```bash
python scripts/select_tests.py fetch-map            # newest map from the "Full tests" workflow (needs gh)
python scripts/select_tests.py --run -- -n 4 -q      # run the selection
python scripts/select_tests.py --explain             # just print what would run and why
```

CI does the same: PRs (`test.yml`) run the selected subset on Linux and the complete unit suite on Windows, each split across four parallel jobs with `--shard K/4` (also usable locally; Windows-only tests and branches are absent from the Linux coverage map); every push to `main` (`test-main.yml`) runs the complete suite on Linux/macOS/Windows, enforces the coverage threshold, and publishes a fresh map to the Actions cache and as the `test-impact-map` artifact. The `ci-full-suite` PR label forces the full suite on a PR.

The Windows legs of both workflows run with `--reruns 1`: a test that fails once and passes on retry keeps the job green and is listed as a "Passed only on rerun" warning annotation on the run, so a flake is visible without opening a `main-red` incident. A test that fails twice still fails the job. The rerun is a backstop, not a fix: a test that shows up in those annotations has a timing or path-identity assumption to remove (sync on an observable event or `synchronization_timeout`, never a fixed `time.sleep`; read a file that another process may replace inside a `FileNotFoundError` guard).

### Type checking

`basedpyright` (pinned in the `dev` extra) checks `vireo/services/`, `vireo/repositories/` and `vireo/pipeline_stages/` in basic mode; the `typecheck` CI job runs it. Errors that predate the checker are recorded in `.basedpyright/baseline.json`, and the run fails only on errors missing from it. Fix a new error instead of adding it to the baseline. Run `basedpyright --writebaseline` only after removing errors, so the baseline shrinks. To widen coverage, add a directory to `include` under `[tool.basedpyright]` in `pyproject.toml` and fix or baseline what it reports. Repositories that bind façade methods with `setattr` from `FACADE_METHODS` declare them as class annotations; `test_type_checking.py` keeps the two lists equal.

`vireo/tests/test_annotation_ratchet.py` holds the directories in its `COVERED_ROOTS` (today `vireo/services/`) at full annotation: every function and method there, nested ones included, annotates each parameter (a method's leading `self`/`cls` excepted) and its return type. There is no baseline, so a new unannotated function fails the test. Shared annotation names live in `services/service_types.py` (`JobDict`, `JsonDict`, `JobResult`, `JobWork`, `ErrorResponse`, the `JsonError` protocol). Typing-only imports go under `TYPE_CHECKING` so annotations never add import cycles. Use `Any` only for genuinely dynamic values, with a comment saying why. To cover another directory, annotate all of it and add it to `COVERED_ROOTS`.

### Function length

`vireo/tests/test_function_length_ratchet.py` caps every function under `vireo/` (outside tests) at 100 lines, counted from the `def` line. The functions already over the cap are listed with their exact current length in `vireo/tests/function_length_baseline.json`; the test fails if an entry differs from the function's length today (grown, or shrunk without lowering the entry, so a shrink cannot be quietly undone), and an unlisted function may not cross the cap. Split a long function instead of adding it to the baseline. After shortening one, run `python vireo/tests/test_function_length_ratchet.py --write-baseline`, which rewrites the file from the tree and exits nonzero without writing if that would raise an entry or add one for a function that newly crossed the cap (only a missing baseline file is written in full); a moved or renamed long function therefore keeps its entry only by hand-renaming its key in the JSON. A stale entry (function deleted, renamed, moved or now under the cap) fails the test until it is removed. The blueprint factories (`create_<domain>_blueprint`, closures by the injection convention) and `CanonicalSchema.create_tables` are exempt; their inner functions are measured individually.

`tests/frontend/function-length.test.mjs` is the same ratchet for the first-party scripts under `vireo/static/` (vendor and `*.min.js` excluded), run by `npm run test:frontend-checks`: 100 lines per function, parsed with acorn, with the over-cap functions listed in `tests/frontend/function_length_baseline.json`. Keys are `<path>:<qualname>`; an anonymous function is named by what it is assigned or passed to (a tagged structured callee/first-string-argument identity for callbacks), a second same-named function in a scope gets an ordinal (`render#2`), literal `%`, `#`, `.`, and `@` in names are percent-escaped to keep those keys distinct; synthesized callback/constructor/return/anonymous contexts use reserved `@kind` tags with structured escaped payloads, preserving member and argument boundaries, and immediately invoked functions are exempt as scope wrappers. Ordinal shifts and length reorderings are admitted only when the complete same-file long-function group matches its tracked `HEAD` implementations one-to-one, byte-identically apart from line endings and at the recorded lengths; missing Git evidence or a changed body fails closed, so run the writer before committing such an insertion. After shortening one, run `node tests/frontend/function-length.test.mjs --write-baseline`; it refuses to raise or add entries, except that a function moved between files keeps its entry only with the same name, length, and byte-identical tracked `HEAD` body (apart from line endings), with its old key absent from every current function; run the writer before committing a file move so tracked source is available and `--allow-new vireo/static/<page>/` admits the functions of a page whose inline template script was just extracted, since the ratchet cannot parse Jinja-bearing inline JS and those functions were long already.

`vireo/tests/test_parameter_count_ratchet.py` caps every function under `vireo/` (outside tests) at 12 parameters: positional, keyword-only, and `*args` and `**kwargs` as one each, not counting a method's `self`/`cls`. The functions already over the cap are listed with their exact current count in `vireo/tests/parameter_count_baseline.json`, and the test fails if an entry differs from the function's count today (grown, or shrunk without lowering the entry) or an unlisted function crosses the cap. Don't add a parameter to a listed function or list a new one: group parameters that mean one thing into a frozen dataclass passed whole, as `scanner.ScanOptions` / `ScanHooks` / `ScanControl` do for `scan()` (settings, callbacks, and cancel/pause probes kept apart; mutable accumulators the function fills stay explicit arguments). After removing parameters, run `python vireo/tests/test_parameter_count_ratchet.py --write-baseline`, which, like the function-length writer, rewrites the file from the tree and refuses to raise or add an entry; a renamed or moved over-cap function keeps its entry only by hand-renaming its key, and a stale entry fails until it is removed.

`vireo/tests/test_photo_safety_invariants.py` is a Hypothesis state machine that runs random sequences of imports (including cancelled and crashed ones), scans, moves, deletes and workspace sharing against a scratch library, and checks after every step that no photo is lost or overwritten, the catalog matches disk, a finished import catalogs the whole card, and no photo drops out of a workspace. PRs run a small derandomized budget; `photo-safety-nightly.yml` runs a large random one (`VIREO_INVARIANTS_PROFILE=nightly` locally). When you add an operation that copies, moves or deletes originals, add it as a rule there. A failure prints the shrunk sequence of steps; keep it as a regression test.

Do not monkeypatch `sqlite3.connect` globally in tests: coverage flushes per-test contexts to its own SQLite file at every test boundary, so a global fake crashes the xdist worker. Fake only the connection for the database path under test (see `test_pipeline_queue.py`).

### Broad exception handlers

`vireo/tests/test_broad_except_ratchet.py` counts the broad handlers in every module under `vireo/` (outside `tests/` and `testing/`): `except:`, `except Exception`, `except BaseException` (alone or in a tuple) and `contextlib.suppress` of either. `vireo/tests/broad_except_baseline.json` holds each module's exact count, so a new broad handler fails, and so does a removed one until its entry is lowered with `python vireo/tests/test_broad_except_ratchet.py --write-baseline` (the writer never raises an entry, and refuses new module entries after bootstrap; a genuine move/split needs a reviewed manual baseline-key migration because matching totals cannot prove movement). Catch what the try body can actually raise (`OSError`, `ValueError`, `sqlite3.Error`, `json.JSONDecodeError`, ...); when a boundary must stay broad (a per-item job loop, best-effort cleanup, a third-party call with an undocumented error set), narrow or remove another broad handler in the same module. Under the test's `DOCUMENTED_ROOTS`, every broad handler must also re-raise, log the traceback (`log.exception` or `exc_info=`), or carry a `# broad: <reason>` comment on the `except` line or the comment lines under it (above the `with` line for `suppress`); a deliberate boundary gets both the log and the reason, and a failure the user should see is surfaced in the response or job status, not just the log (CORE_PHILOSOPHY.md, "No black boxes"). Add a directory or module to `DOCUMENTED_ROOTS` once it is clean.

### Browser tests

`tests/e2e` is excluded from the default `addopts`, so the browser suite only runs
when asked for by name. It is timing-sensitive: under machine load a page load can
stall past a locator's 30s timeout and fail a test that has nothing wrong with it.
The release gate (`e2e-full.yml`) absorbs that with reruns — match it locally rather
than chasing a one-off red line.

`pip install -e ".[dev]"` installs the Playwright Python package but not the browser
binary, so a clean checkout needs the one-time download first (add `--with-deps` on
Linux to pull the system libraries too, as `e2e-full.yml` does):

```bash
python -m playwright install chromium
python -m pytest -o addopts='' -q tests/e2e/ --reruns 2 --reruns-delay 1
```

Reruns retry only the failed test, with fresh fixtures. A genuinely broken test still
fails all three attempts; only one that passes on retry is tolerated.

## Architecture

Layering: `vireo/app.py` wires the app; HTTP routes live in blueprints under `vireo/web/`; workflow, filesystem and cache logic lives in `vireo/services/` (which never imports from `vireo/web/`); SQL lives in `vireo/repositories/` (and the canonical schema in `vireo/canonical_schema.py`), behind the `Database` façade in `vireo/db.py`. See `docs/ARCHITECTURE.md` for the boundaries.

**Injection convention.** Every blueprint is built by `create_<domain>_blueprint(get_db, json_error, ...)`. A factory takes only per-app state: the request DB getter, `json_error`, the job-runner getter (`lambda: app._job_runner`), `db_path` / `app.config`, and methods of per-app service instances, which `create_app` passes as bound methods at registration (e.g. `run_batch_delete=photo_deletion.run_batch_delete`). Objects a blueprint uses as a unit (`VisualScope`, `LocationErrors`, `InatTokenGeneration`) are passed whole. Pure helpers, constants and module-level locks are imported by the blueprint module, never threaded through `create_app`.

- `vireo/app.py` — App factory and wiring, created via `create_app(db_path, thumb_cache_dir, api_token)`, plus `main()`, the startup cache migrations/quota passes, and the mount-aware Trash helpers (`_trash_paths`, `_network_volume_roots`, `_path_on_network_volume`, ...; tests patch these on the `app` module, so blueprints and `PhotoDeletion` receive late-binding lambdas around them). `create_app` builds the per-app objects (`_get_db`, the `JobRunner`, `RenderCache`, `PhotoDeletion`, `StartupTasks`, `MissingOriginals`, `VisualScope`, `BulkGpsLocations`, `FolderMoves`, `PipelineChain`, `build_scan_work`), runs the startup catalog repairs (`StartupTasks.run_catalog_repairs`), registers the request hooks and every blueprint, and adds the `/api/v1` aliases. It defines no routes: `test_no_new_routes_in_app_py` holds the limit at zero. Missing-originals invalidation is captured by `FolderMoves`, `build_scan_work` and `PipelineChain` at construction, so `missing_originals` is built before them.
- `vireo/db.py` — `Database` class. SQLite with workspace support. Auto-creates Default workspace and restores last-used workspace on init.
- `vireo/repositories/` — Per-domain SQL behind the `Database` façade, one module per domain (`<domain>.<Domain>Repository`); each module's docstring says what it owns and what deliberately stays on `Database`. Conventions: each domain's repository is built on `self.conn` by `Database._<domain>_repository(...)`, which passes the active workspace id (or `self._ws_id` as a callable where resolution is lazy), `commit_with_retry`, and module constants in explicitly. Simple persistence operations are reached through a domain accessor — a `Database` property that returns a fresh repository from that factory on every access (`db.job_history.get(job_id)`; never cache or hold one across `set_active_workspace`; a domain mixing workspace-scoped and id-addressed operations has its factory pass `self._ws_id` uncalled, so one accessor serves both and only the scoped methods resolve the workspace, e.g. `db.pending_archives`) — while coordinated workflows (anything that does more than forward one call, such as `photo_ingest.add_photo` resolving duplicates after the insert, and cross-domain composition) live in `vireo/services/` as functions taking `db`, and `Database` keeps the process caches, the active-workspace state and the methods a contract or a repository binds by name. Older domains still expose one-line forwarding wrappers; `FORWARDING_WRAPPER_LIMIT` in `test_db_facade_structure.py` caps their count, which may only shrink: move a domain's callers onto its accessor, delete its wrappers, and lower the cap (domains with safety contracts keyed to wrapper names, `tag_photo` for keyword provenance and the review-decision writers in `test_route_contract.py`, migrate last and must keep those contracts detecting calls); every `photo_keywords` writer that creates or converges an association lives in `repositories/keyword_provenance.py`, and other domains reach it through the façade (`self.tag_photo(...)`) so `test_keyword_provenance_contract` sees each call site; `repositories.UNSET` is the shared "argument not provided" sentinel. Each domain's `vireo/tests/test_db_<domain>.py` has a structural test that fails if a moved method touches `self.conn` again, and `vireo/tests/test_db_facade_structure.py` holds the whole class to it: outside `__init__`, `close`, `_commits_held` and the transaction-control methods, a `Database` method may only hand `self.conn` to a repository. `vireo/tests/test_sql_boundary.py` holds callers to the same line: nothing outside `db.py` and `vireo/repositories/` touches `_active_workspace_id` or `_ws_id()`, and each module's `<expr>.conn` uses are capped at their current count — put new SQL in a repository behind a `Database` method, and lower the cap when you move some. Callers control transactions through `db.commit()`, `db.rollback()`, `db.in_transaction`, `db.begin()`, `db.begin_immediate()` and `with db.transaction():` (each the one connection call it names, the last being `with db.conn:`; `commit()` stays a no-op while `_commits_held` holds commits, `transaction()`'s exit commit does not), plus `db.commit_with_retry()` (the module's `commit_with_retry` on this connection), never `db.conn`. `conn` exists only while the connection is open (`close()` deletes it rather than setting `None`, so its type is never Optional); ask `db.closed`, not `db.conn is None`, and close through `db.close()`, never `db.conn.close()` (`test_sql_boundary.py` forbids the raw close, including through a local alias of `conn`, in every first-party Python file; only the body of `Database.close` is exempt). New domains document themselves in their module docstring, not on this line.
- `vireo/canonical_schema.py`, `vireo/schema.py` — The schema. `CanonicalSchema.create_tables` builds every table, index, trigger and view (`IF NOT EXISTS`) and stamps a fresh catalog with `SCHEMA_VERSION`; `schema.MIGRATIONS` holds the numbered changes that bring an older catalog to that shape, each run once at startup in its own transaction after `_snapshot_before_migrations` has written a `.pre-v<N>.bak`. No other module creates schema: objects that used to be created on first write (`job_history`, `preview_cache_invalidations`, `species_identity_repairs`, the common-name lookup index) are `canonical_schema.FORMERLY_LAZY_OBJECTS`, and `vireo/tests/test_schema_ddl_boundary.py` caps DDL outside the schema modules at its current count (one scratch index in `repositories/working_copies.py`), which may only shrink. A new object goes in `create_tables` plus a migration; `python vireo/tests/test_db_canonical_schema.py --update` regenerates the schema snapshot.
- `vireo/duplicates.py` — Pure exact-duplicate resolver (winner/loser decision + metadata merge). Consumed by `duplicate_resolution.apply_duplicate_resolution` and the scan job.
- `vireo/import_dedup.py` — Metadata-first duplicate gate for imports (`CatalogIndex` + `DuplicateChecker`): match by (filename, size, EXIF capture time) with a content-hash fallback for missing/placeholder metadata; `verify_by_hash` restores hash-everything. Shared by `ingest()`, `/api/import/check-duplicates`, and the local-processing preflight so duplicate previews always agree with what ingest actually skips.
- `vireo/jobs.py` — `JobRunner` for background tasks (scan, classify, thumbnails, etc.) with SSE progress streaming. Final status follows the rollup rule: a work function that returns normally after recording anything in `job["errors"]` ends "failed", not "completed"; a result carrying `"ok"` is the job's own verdict instead (its `errors` are folded into the tally either way), so a job whose errors list includes notices that are not failures (the import's card-safety lines) must set `ok`. Either way the result keeps its counts and the summary leads with them. `JobRunner` is the coordinator and public API; its state lives in collaborators under `vireo/job_runner/` (history, checkpoints, worker threads, event streams, step tree, cancel/pause control, pipeline queue, workspace reservations), all sharing the runner's one lock; the package docstring says who owns what, and the rollup rule itself is `job_runner.outcome.apply_result_verdict`. Everything on a job dict, `_`-prefixed keys included, is published: `/api/jobs` and `/api/jobs/<id>` jsonify its snapshot on every poll, so it may hold only JSON values. Keep worker-private state such as sets of photo ids on the worker (the classify job's `DetectionHandoff`), not on `job`. The test suite's `_shutdown_created_job_runners` fixture checks every snapshot and every job left in a runner and fails the test on a value JSON cannot encode (`vireo/tests/job_json.py`).
- `vireo/scanner/` — `scan(root, db, *, options=ScanOptions(...), hooks=ScanHooks(...), control=ScanControl(...))` and its helpers, one module per responsibility: `scan_run` (`scan()` and `_ScanRun`, the orchestrator that runs the phases in order; metadata extraction and the end-of-scan pairing and working-copy pass stay there), the phase collaborators `discovery`, `folders`, `triage` (incremental pre-pass), `features` (hashing), `indexing` (per-file catalog writes), `companion_keep` / `companion_attach` (companion JPEGs) and `run_state` (the cancel/status signals and the progress/counts tally they share), `options`, `hashing`, `keywords`, `companions` (RAW+JPEG pairing), `cache_invalidation`, `working_copies` / `working_copy_batch`. `scanner/__init__.py` re-exports what code outside the package imports. A module inside the package looks names up in its own globals, so a test patches `scanner.<module>.<name>` where the name is called (e.g. `scanner.scan_run.extract_metadata`), not `scanner.<name>`. Its SQL lives behind `db.scanning`, `db.companion_pairing` and `db.working_copies`.
- `vireo/pipeline_stages/` — Processing stage implementations with explicit per-run state and dependencies. `pipeline_job.py` owns scheduling, pause participation, locks, and final failure reporting; stages do not import it. See `docs/ARCHITECTURE.md` for state ownership and cancellation boundaries.
- `vireo/classify_job/` — The standalone classify job, a package with one module per responsibility (`label_loading`, `gating`, `cache_coverage`, `label_source`, `detection`, `classify_pass`, `store_predictions`, `cached_only`, `run` / `job_run` / `run_helpers`; shared types and the optional model imports in `common`). `__init__.py` re-exports what code outside the package imports (`run_classify_job`, `ClassifyParams`, `describe_label_source`, and the helpers the pipeline stages read through the package). Patch a name in the submodule that looks it up (`classify_job.detection.detect_animals`): a patch of `classify_job.<name>` reaches only callers that read the package attribute.
- `vireo/import_job/` — The import job (`run_import_job`: copy card → archive, hash-verify, catalog per batch), one module per responsibility; the package docstring maps them. `__init__.py` re-exports only what callers outside the package import, and its catalog SQL is `db.imports` (`repositories/imports.py`). Tests patch a helper in the module that looks it up (`import_job.planning.IMPORT_BATCH_SIZE`), or with `import_job_patching.patch_import_job` when several modules do.
- `vireo/config.py` — Global config read/write from `~/.vireo/config.json`, the `_migrations_applied` marker list for config migrations, and the settings-write plumbing every route that rewrites the file shares: `read_raw_config_file()` (the on-disk dict without DEFAULTS merged, preserving a `.corrupt` backup) and `settings_write_lock` (module-level, because `config.json` is process-global).
- `vireo/file_replace.py` — `replace_file(src, dst)`, the only way production code publishes by rename: exactly `os.replace` off Windows, and on Windows it retries a transient `PermissionError` (Defender, the indexer or an editor briefly holding the destination). `test_production_code_publishes_through_replace_file` fails on a bare `os.replace`.
- `vireo/mcp_server.py` — The MCP server (`vireo-server --mcp` / `python vireo/app.py --mcp`, dispatched in `main()` before the single-instance guard): stdio tools for Claude Code, Claude Desktop and other MCP clients, built on the `mcp` SDK's `MCPServer`, calling the running app over HTTP with the `runtime.json` token (`VIREO_URL` / `VIREO_TOKEN` override) and never opening the database or spawning an instance. Tools are registered in groups under 100 lines each; a failure the user should read is raised as `VireoError` (a `ToolError`), since any other exception reaches the client as a bare "Error executing tool". `connect_info()` builds the Claude Code / Claude Desktop configuration that `/api/system/mcp-config` serves to Settings. Tests drive the tools through a Flask test-client transport and one real stdio session.
- `vireo/sql_chunks.py` — `chunked(seq, size=SQL_PARAM_CHUNK)`, the IN-clause chunker for caller-sized id lists (re-exported as `app._chunked`; tests patch it there).

### Shared request plumbing (`vireo/web/`)

- `vireo/web/app_hooks.py`, `vireo/web/responses.py` — App-wide request plumbing. `web.responses`: `json_error` (the one JSON error shape, stamped with `g.request_id`) and `photo_not_found_error`. `web.app_hooks`: `get_request_db(db_path)` / `close_request_db` (the per-request `Database` on `g`), `RESERVATION_EXEMPT_ENDPOINTS`, and `register_app_hooks(app, get_db=..., reservation_exempt_endpoints=...)`, which installs request timing/ids, the browser-surface guard, the `/api/v1` token check, the workspace mutation reservation and its release, request logging with the security headers and session cookie, and the uncaught-error handler — `before_request` order is part of the security contract (`test_app_hooks_run_in_security_order`). `create_app`'s `/api/v1` alias loop adds `v1_<view>` to the exempt set it passed in.
- `vireo/web/request_args.py` — The `flask.request` parsers (`request_bool_arg`, `request_rules_arg`, `request_visual_arg`, `request_flag_filter`, `request_location_status_filter`, `dashboard_scope_args`, `request_missing_originals_folder_id`), `focus_candidate_ids`, the `MAX_SELECTION_PHOTOS` / `MAX_FOCUS_PHOTO_IDS` / `MAX_PER_PAGE` caps, and the guards that answer with a response (`reject_visual_collection`, `parse_selection_photo_ids`), which take `json_error` as a keyword. It re-exports `coerce_collection_id` from `services.visual_scope`.
- `vireo/web/background_jobs.py` — `@background_job` decorator + `JobLaunch` context. Every route that starts a job takes `ctx` as its first argument, opens worker DBs with `ctx.thread_db()`, and returns `ctx.start(job_type, work, ...)`.
- `vireo/web/location_edits.py` — Location-edit helpers shared by the location, place, batch keyword/location, and location-review routes: request parsing (`extract_place_id`, `extract_keyword_id`, `normalize_client_place_details`), location payloads (`serialize_photo_location`, `walk_parent_chain`, `location_name_conflict_payload`/`_response`, `LOCATION_NAME_PIPE_ERROR`), and `LocationErrors` — the error responses bound to `json_error`, built once in `create_app` as `location_errors`. Keyword and GPS sidecar queueing with add/remove cancellation lives in `vireo/services/pending_changes.py`; Google result-language handling (`result_language`, `place_details_for_language`, `reverse_geocode_for_language`) in `vireo/places.py`.

### Blueprints (`vireo/web/`)

- `vireo/web/pages.py` — HTML pages: the plain template routes, `/` and `/welcome` (redirect on classification readiness / `setup_complete`), `/config-defaults.js` (the `window.VIREO_*` globals `_navbar.html` loads first), and `/favicon.ico`.

- **Module pages** (`frontend-module-pages.json`) — the target shape for page JS, replacing classic scripts that share page globals. A module page's template loads one entry, `<script type="module" src="/static/<page>/boot.js">`, with no inline `<script>` and no `on*=` attributes; every other file in `vireo/static/<page>/` is an ES module reached through `boot.js`'s relative `./name.js` imports. Page state is one exported `state` object in `state.js` (other modules write its fields; they cannot reassign an imported `let`); events are bound with `addEventListener` in `boot.js` or delegated listeners, and rendered markup carries `data-*` attributes instead of inline handlers. Rendered markup that needs a handler names it in a page-specific attribute bound by the page (Browse's `data-browse-on`, see its README). Page files reach shared code only through the page's `shared.js`, never by bare name: it reads the globals the navbar's bridge (`navbar-globals.js`), the filter bar, `vireo-utils.js` and the other classic shared scripts publish (call-time forwarders, keeping the old `typeof` guards), so the page's type-check project does not pull in the navbar's modules; and the page functions the navbar and lightbox call (`afterHistoryChange`, `getActiveSelection`, ...) are registered as page hooks through `shared.js`'s `registerPageHooks()` (`vireo-page-hooks.js`, above), listed per page as `pageHooks`. A module page writes no `window` globals; `sharedWrites` lists the shared-script latches a page may still write there (none for Misses; Browse writes the native menu's photo override, the navbar's shortcut config and the Google Maps callback name). Enforcement: `eslint.config.mjs` reads the list and lints those directories as modules with `no-undef`/`no-unused-vars` and `no-restricted-syntax` against `window`/`globalThis` writes (outside `sharedWrites`), inline-handler strings, `on*` properties and `setAttribute('on…')`; `vireo/tests/test_module_pages.py` checks the template, that every file is reached from `boot.js`, and `pageHooks` against the page's `registerPageHooks` calls. Module scripts are deferred, so `boot.js` runs after parsing and before `DOMContentLoaded`, like a classic script at the end of `<body>`. Tests reach module state through `tests/e2e/module_pages.py` (a test-side `import()` returns the page's own instances): `import_page_modules()` imports named modules once, and the `page` fixture publishes all of Browse's as `pageModules.<camelCasedFile>` with its state as `browseState` after every navigation; and `page_with_scripts` inlines a module entry's whole import graph. Card cleanup (`vireo/static/card-cleanup/`) and the Dashboard (`dashboard/`, template `stats.html`) are module pages too, each with a README. Workspace (`vireo/static/workspace/`), Welcome (`welcome/`, which has no navbar and so its own `safeFetch`) and Audit (`audit/`) are module pages, each with a README mapping its files. To convert a page: move its route from `SPLIT_PAGES` in `test_inline_page_scripts.py` to `frontend-module-pages.json`, follow `vireo/static/misses/README.md`, and keep `tsconfig.frontend-pages/<page>.json` listing every file.

## Workspaces

Each workspace scopes predictions, collections, pending changes, and visible folders. Photos and keywords are global (shared across workspaces).

- `Database.__init__` auto-creates "Default" workspace and restores the last-used workspace (by `last_opened_at`).
- Workspace-scoped methods use `self._ws_id()` which raises `RuntimeError` if no workspace is active. Outside the data layer, read it with `db.active_workspace_id` (`None` when unset) or `db.require_workspace_id()` (raises).
- Background job threads must call `thread_db.set_active_workspace(active_ws)` after creating a `Database` instance.
- Per-workspace config overrides are stored in `workspaces.config_overrides` (JSON column). Use `db.get_effective_config(cfg.load())` to get config with workspace overrides applied.

## Workflow

**All feature work, bug fixes, and non-trivial changes MUST be done in a git worktree.** Do not make changes directly on `main`. At the start of any implementation task, create a worktree before writing code.

1. Create a worktree and feature branch for the task.
2. Do all implementation work in the worktree.
3. Run tests before finishing. Preferred: `python scripts/select_tests.py --run -- -n 4 -q` (after `fetch-map`), which runs exactly what your diff can affect. Fallback when no map is available: `python -m pytest tests/test_workspaces.py vireo/tests/test_db.py vireo/tests/test_app.py vireo/tests/test_photos_api.py vireo/tests/test_edits_api.py vireo/tests/test_jobs_api.py vireo/tests/test_darktable_api.py vireo/tests/test_config.py -v`
4. **Create a PR** using `gh pr create`. Include what changed and test results in the PR description.
5. When review feedback arrives, push fixes to the **same branch**. The review bot re-reviews automatically on push.
6. Squash-merge when approved.

## Debugging tips

- Slow page navigation? Check if the bottom panel's SSE log stream or job polling is consuming Flask threads. The SSE stream and polling only run when the panel is open.
- Request timing is logged for all API calls at INFO level and slow requests (>0.5s) at WARNING level.
- The Flask dev server is single-process with threading. Long-running SSE connections can exhaust the thread pool.

## PR Agent System

Automated review cycle managed by `.github/workflows/pr-agent.yml`.

### How it works

1. Someone comments `/claude-fix` on a PR to activate the agent.
2. Claude reads review comments and pushes fixes to the **same branch**.
3. When a review is submitted on a `claude-agent` PR (not an approval), Claude pushes fixes to the branch.
4. When **Codex Connect** submits a review on any PR, Claude addresses the feedback by pushing to the branch and adds the `claude-agent` label so future comments are handled automatically.
5. When the **Tests workflow fails** on any PR, Claude reads the failure logs and pushes a fix directly to the PR branch. Loop prevention: skips if the failing commit was already a CI fix attempt.
6. When **Full tests fails on `main`**, `main-health.yml` opens (or comments on) a `main-red` issue and closes it on the next green run. It also fires the routine with `Task: fix-main` until one request per incident has been accepted (the issue records it), and the routine opens a `fix-main` PR; to retry after that, close the issue and the next red run opens a new one. The fire is gated on the repository variable `MAIN_HEALTH_ENABLE_FIX_MAIN`, off by default because the stored routine prompt is not synced from the repo; flip it to `true` after pasting `pr-agent-routine-prompt.md` into the routine. Runs on `main` are never cancelled mid-run (a burst of merges queues one run for the newest), so main always gets a complete result.
7. When an **approving review** is submitted or someone comments **👍**, the PR is squash-merged. Merges made with `GITHUB_TOKEN` start no push workflows, so each merge job then dispatches `Full tests` on main (and the website deploy when `website/` changed) through `.github/actions/post-merge-dispatch`.
8. Branches are deleted after merge.

### Key files

- `.github/workflows/pr-agent.yml` — Event forwarder + pure-bash merge jobs
- `.github/workflows/main-health.yml` — Tracks red `Full tests` runs on `main` and fires `fix-main`
- `.github/actions/fire-routine/action.yml` — Composite action that POSTs to the routine `/fire` endpoint
- `.github/actions/post-merge-dispatch/action.yml` — Starts `Full tests` (and the website deploy) on main after a bot merge
- `docs/pr-agent-routine.md` — Setup guide for the Claude Code routine that does the LLM work
- `docs/pr-agent-routine-prompt.md` — The routine's prompt (paste into claude.ai/code/routines)

### Architecture

LLM work runs in a Claude Code routine (billed against the Code subscription, not the Anthropic API). The GHA workflow only classifies events and fires the routine with a text payload. Three merge jobs remain pure bash. See `docs/pr-agent-routine.md`.
